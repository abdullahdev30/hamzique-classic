===========================================================

Project root: C:\work\project\ecommerce-store

Main Payload config: src/payload.config.ts


1. HIGH LEVEL ARCHITECTURE
==========================

This project is a single Next.js application that serves both:

1. The public ecommerce storefront
2. The Payload CMS admin panel and APIs

The frontend is inside:

  src/app/(app)

The Payload admin/API routes are inside:

  src/app/(payload)

Payload is not a separate backend server in this project. It runs inside the same Next.js app. Frontend server components call Payload directly with the Payload Local API:

  import { getPayload } from 'payload'
  import configPromise from '@payload-config'

  const payload = await getPayload({ config: configPromise })

The main connection point is:

  src/payload.config.ts

That file defines the database adapter, admin user collection, custom collections, globals, editor, plugins, storage, and generated TypeScript output.


2. REQUEST FLOW: HOW A PAGE LOADS
=================================

Basic public page request:

1. Visitor opens a URL such as /, /men, /women, /shop, or /products/my-product.
2. Next.js matches the route under src/app/(app).
3. The route component runs mostly on the server.
4. The route calls Payload through getPayload({ config: configPromise }).
5. Payload queries PostgreSQL using the configured collections.
6. The server renders HTML with the CMS data.
7. Small client components hydrate only where interactivity is needed, such as cart, auth, theme toggle, variant selector, gallery, and checkout.

Example page flow for /men:

  src/app/(app)/[slug]/page.tsx
    -> queryPageBySlug({ slug: 'men' })
    -> Payload collection: pages
    -> RenderHero(page.hero)
    -> RenderBlocks(page.layout)
    -> CategoryProductSection(page)
    -> Payload collection: categories
    -> Payload collection: products

Example product flow for /products/black-shirt:

  src/app/(app)/products/[slug]/page.tsx
    -> queryProductBySlug({ slug: 'black-shirt' })
    -> Payload collection: products
    -> product gallery, description, sizes, colors, variants, inventory, related products
    -> AddToCart uses ecommerce plugin client cart API

8.10 Checkout and Cash on Delivery
----------------------------------

Files:

  src/app/(app)/checkout/page.tsx
  src/components/checkout/CheckoutPage.tsx
  src/payments/cashOnDelivery.ts

Flow:

  - Customer or guest opens /checkout.
  - If logged in, email comes from user.
  - If guest, visitor enters email.
  - Billing address is selected or created.
  - Shipping can be same as billing or separate.
  - User clicks "Place cash on delivery order".
  - Checkout calls initiatePayment('cashOnDelivery').
  - cashOnDeliveryAdapter creates a transaction.
  - Checkout calls confirmOrder('cashOnDelivery').
  - cashOnDeliveryAdapter creates an order, marks cart purchasedAt, links transaction to order.
  - Cart is cleared.
  - User is redirected to /orders/[orderID].

Cash on Delivery settings:

  src/lib/ecommerceDefaults.ts

  Currency: PKR
  Country: Pakistan
  Payment method: cashOnDelivery

9. PAYLOAD LOCAL API USAGE
==========================

This project mostly uses the Payload Local API in server code instead of calling HTTP APIs from server components.

Common pattern:

  const payload = await getPayload({ config: configPromise })
  const result = await payload.find({
    collection: 'pages',
    where: { slug: { equals: slug } },
  })

Important files using Local API:

  src/app/(app)/[slug]/page.tsx
  src/app/(app)/[slug]/[category]/page.tsx
  src/app/(app)/products/[slug]/page.tsx
  src/app/(app)/shop/page.tsx
  src/app/(app)/(account)/account/page.tsx
  src/app/(app)/(account)/orders/page.tsx
  src/app/(app)/(account)/orders/[id]/page.tsx
  src/components/Header/index.tsx
  src/components/Footer/index.tsx
  src/components/CategoryProductSection/index.tsx
  src/components/forms/FindOrderForm/sendOrderAccessEmail.ts

Security note:

  Payload Local API bypasses access control by default.
  When querying on behalf of a real user, this project passes:

    user
    overrideAccess: false

  This is visible in the account and orders routes.

For public content queries, this project also filters by published status in route logic, for example:

  _status equals published

12. SECURITY FLOW
=================

Main access files:

  src/access/adminOnly.ts
  src/access/adminOrPublishedStatus.ts
  src/access/adminOrCustomerOwner.ts
  src/access/adminOrSelf.ts
  src/access/isAdmin.ts
  src/access/isDocumentOwner.ts
  src/access/adminOnlyFieldAccess.ts
  src/access/customerOnlyFieldAccess.ts

Important rules:

  - Only admins can create/update/delete pages.
  - Only admins can create/update/delete categories.
  - Only admins can create/update/delete media.
  - Everyone can read public media.
  - Everyone can read published pages/products.
  - Draft pages/products require admin preview.
  - Customers can access only their own account data/orders/addresses.
  - Guest order access requires email + accessToken.

Anti-XSS and safe rendering:

  - Most content is rendered through React components and typed Payload data.
  - Product JSON-LD uses dangerouslySetInnerHTML, but JSON is stringified and "<" is escaped.
  - Rich text content comes from Payload Lexical data and is rendered through project components.
  - Preview path requires PREVIEW_SECRET and authenticated Payload user.

15. ADMIN CONTENT WORKFLOW
==========================

Recommended editor workflow:

1. Log in to /admin with an admin user.
2. Upload media and set alt text.
3. Create or edit Pages.
4. Add hero content and page layout blocks.

16. CUSTOMER FLOW
=================

Visitor shopping flow:

1. Visitor lands on home or a CMS page.
2. Header navigation is built from CMS global links, published pages, and categories.
3. Visitor opens a category page or shop page.
4. Product lists are fetched from Payload.
5. Visitor opens a product detail page.
6. Product details, images, variants, prices, discounts, inventory, sizes, colors, and related products come from Payload.
7. Visitor selects a variant if needed.
8. Visitor adds the product to cart.
9. Cart is managed through ecommerce plugin client hooks.
10. Visitor opens checkout.
11. Visitor logs in or checks out as guest.
12. Visitor selects/adds address.
13. Visitor places Cash on Delivery order.
14. Payload creates transaction and order records.
15. Visitor lands on the order detail page.

Registered customer account flow:

1. Customer creates account or logs in.
2. Customer can view account settings.
3. Customer can manage addresses.
4. Customer can view orders.
5. Customer can view individual order details.

Guest order flow:

1. Guest places COD order with email.
2. Order stores customerEmail and accessToken.
3. Guest can use /find-order with email and order ID.
4. Server sends a secure access URL if the order exists.
5. Guest order page verifies email and accessToken before showing details.

20. SUMMARY
===========

Payload controls the store data, page content, navigation data, media, SEO, products, categories, customers, carts, addresses, orders, transactions, and forms.

Next.js controls the route structure, rendering, UI components, theme system, checkout screens, account screens, product page layout, and frontend behavior.

The two sides are linked through:

  src/payload.config.ts
  @payload-config alias
  getPayload({ config: configPromise })
  Payload REST routes under /api
  Payload ecommerce client hooks
  Generated types in src/payload-types.ts

The most important mental model:

  Payload is the source of truth for content and commerce records.
  Next.js is the rendering layer and interaction layer.
  Server components fetch Payload data directly for fast SSR.
  Client components use the ecommerce/auth APIs only where live interaction is required.
